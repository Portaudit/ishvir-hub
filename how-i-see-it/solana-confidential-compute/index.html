Solana Confidential Compute: What It Is and What It Proves

By Ishvir Jackpersad · As of 22 November 2026 · Drafted with AI assistance, see How I build

Solana Confidential Compute is a toolkit that lets an app check, on Solana, that an AI answer came from hardware-isolated memory. The Solana Foundation and the private AI startup Nito (tryNito.ai) launched it on 13 November 2026 as an open-source, unaudited beta on devnet, and the Foundation says to use it for development only.

Summary

The release has three parts: an open-source SDK, an onchain program that records hardware verification results, and a chat starter template. The hardware check proves which machine setup signed an answer. It does not prove the answer is correct, and the Foundation's product page says the first chat does not yet use the onchain program (section 5).

This guide explains the problem it targets, how the pieces fit, who runs what, what the beta can and cannot show, and what to ask before relying on it. It is written as of 22 November 2026, nine days after launch, from the Foundation's launch post and product page on solana.ai, its X thread, press coverage and published security research. I rechecked the product page and AMD's advisory on 22 November and found no change in audit or mainnet status. Where sources differ, the text says so. It was drafted with AI assistance.

1. The scenario: private AI and the trust gap

People now send AI services personal conversations, internal documents and trading strategies. When a provider says those inputs stay private, users usually have to take its word for it.

Confidential computing is one answer. As the Foundation describes it, a trusted execution environment (TEE) is a hardware-backed space that isolates code and data from the host operating system and the infrastructure operator. Data stays protected while it is being processed, not only while stored or sent.

A second problem follows. Even if a provider runs a TEE, outsiders need a way to check that claim. TEEs support this with attestation: a signed statement from the hardware about what is running inside the protected section. Solana Confidential Compute aims to make that check public and reusable by putting its result on a blockchain.

2. What was released

The launch centres on an open-source SDK and an onchain verification program. The Foundation also published a Confidential Chat developer template built with Next.js and React. The product page also lists Rust and TypeScript SDKs, helpers for checking the verifier's record from your own program, a daemon that runs inside the enclave, a command-line tool and a Docker image.

Part What it does
SDK (open source) Developer software for building private AI apps and checking the hardware behind them
Verification program (onchain) Checks hardware reports and records the result on Solana
Confidential Chat template A starter app for private AI chat

The release sits on solana.ai, a new hub for AI on Solana. The Foundation presents the same components as reusable by other teams, and Nito is building them into its own private AI platform.

3. How it works

Setup
  1. A protected machine makes a signing key inside itself.
  2. The hardware signs a report linking the key to a recent Solana slot.
  3. The onchain program checks the report and records the key, hardware type and expiry.
Use
  1. The machine signs AI responses with that key.
  2. An app checks the signature against the onchain record.
  3. The app accepts or refuses the output.

The two boxes show 3 setup steps and 3 use steps. It is my summary of the sources, not a figure from the Foundation.

A protected machine makes a signing key inside itself. The hardware produces a signed report that links the key to a recent Solana slot, and the onchain program checks the report and records the key, the hardware type and an expiry date. The machine then signs AI responses with that key, and an application checks the signature against the onchain record before accepting the output.

The AI work itself happens off-chain, so conversations and private inputs are not published to the blockchain. Only the verification record goes onchain.

4. Who built and runs what

The launch post says the Nito team built the toolkit in coordination with the Solana Foundation, while the Foundation's announcement says it was built with Nito. Nito is an AI platform that routes requests to the protected environment and is a required part of the chat template's setup. Nito describes itself as a chat service that runs chats through privacy-preserving hardware. The product page says the server and Nito cannot read the prompt or the reply, which is a claim about access, not about what is stored.

In the chat template, a message takes this route, according to the same coverage:

  1. The browser checks the confidential machine's attestation before encrypting the message. If the check fails, the prompt is not sent.
  2. The encrypted message passes through an application server and Nito to a protected environment running the model.
  3. The response is encrypted before it returns. By design, the intermediaries cannot read the contents.

Who owns the hardware. The product page says the chat's model runs in confidential hardware through Tinfoil's confidential router, with Nito passing the encrypted prompt along. The launch post separately names Nito as the operator of its own confidential hardware for its private AI platform, so they describe two deployments: the chat on solana.ai, and Nito's own platform. For the verifier itself, the product page names AMD SEV-SNP on Google Cloud Confidential VMs, AWS Nitro Enclaves and Google Confidential Space. Neither page says who would run hardware for other developers. The product page lists AWS Nitro Enclaves alongside AMD SEV-SNP; Nitro Enclaves is a separate AWS technology, not AMD SEV-SNP. solana.ai describes itself as presenting products and teams building AI on Solana, and I found no evidence that it operates the confidential hardware, although it does run the chat's application server.

6. What the shipping chat actually proves

The one piece a developer can run today is the Confidential Chat template, and its README is specific about what it does and does not prove.

  • What is checked. The browser verifies the enclave's attestation offline, against a repository pinned in the page code, and then encrypts the chat to the verified key. If the check fails, nothing is encrypted or sent. Nito relays the ciphertext to an enclave running Tinfoil's published router code.
  • No fresh challenge. The README says the attestation is not tied to a fresh challenge. Verification shows the key belongs to a genuine enclave running a published release, not that the attestation was produced just now. The product page describes freshness as part of the onchain verifier's check, and the chat does not use that verifier yet.
  • The host is not proved. The page shows which host the request was routed to, and the README says this is not part of the proof.
  • What you still trust. The page code you serve, since a changed page could send plaintext; the chip maker's signature on the report; and Tinfoil's router code, which verification shows is a published release but not that it is free of bugs.
  • What stays visible. Your server sees visitors' IP addresses. Nito sees the time, the model, the account and the size of each encrypted request. The enclave reads the prompt, because it has to in order to run the model.
  • Cost abuse. The output-token cap sits inside the encrypted request, so the server cannot enforce it. Only the byte cap, rate limits and the key's spend cap bound what a caller can spend, and the template leaves rate limiting and sign-in out on purpose.
  • No Solana step described. The README describes no step that reads or writes Solana, which fits the product page saying the chat does not use the onchain verifier yet. I did not see the template's package list. Analytics Insight reports that the template needs a funded Nito account and an API key, and a search excerpt of the Solana Compass article (which I could not open in full) says the chat's router runs the GPT-OSS 120B model.

7. Use cases the launch describes

The Foundation lists personal assistants, agents that handle confidential business data, and private trading strategies. The launch post adds systems that accept instructions or decisions only when signed by verified machines, such as AI rulings for prediction markets or insurance claims, and governance decisions. One summary also mentions sovereign trading agents and autonomous decentralized organizations.

These are possibilities as presented at launch. The product page presents a second product built on the toolkit: Milo, an autonomous trading agent. That is the page's claim. I did not find a published attestation record for the hardware Milo runs on, and the product page does not link one. Treat the other use cases as directions rather than shipped products.

8. What it proves and what it does not

Attestation proves something about a machine, so read each claim for what it covers. The limits below apply to confidential computing in general and to any early beta, not only to this release.

What it can show. The hardware report identifies the protected environment and the software inside it, and the onchain program records the key, hardware type and expiry. An app can then refuse outputs signed by a key with no valid record. For the chat, the product page says each reply links the router's public build record and source code, so you can check them. The product page says the check covers the hardware chip signature, whether the code is on an approved list, and freshness so old proofs cannot be replayed, and that reading the record costs a program at most 1,500 compute units.

What it does not show.

  • That an answer is correct or fair. A signature shows which setup produced the answer, not whether the model was right. This is general background, not a claim from the sources.
  • That metadata is hidden. The product page says the server sees when a prompt is sent, its size and the user's network address, and Nito sees the request and its size. The template README says Nito sees the time, the model, the account and the size of each encrypted request.
  • That the app is safe to run in public. Developers must add their own authentication, rate limits and abuse protections.

What attestation generally protects against. This is general background on how trusted execution environments are usually assessed. Neither the launch post nor the product page says which of these attackers the design targets. The product page does say the host cannot read sealed code and that keys are made in hardware and never leave it.

Attacker Typical coverage
Malicious operator or cloud administrator acting through software In scope by design: the workload is isolated from the host operating system, the hypervisor and firmware, and attestation lets outsiders check this. Researchers have still shown that a malicious hypervisor or firmware can break SEV-SNP, for example forging attestation reports (Fabricked, April 2026).
Compromised host software Software attacks on the host are in scope by design, but denial of service is out of scope, so availability is not protected. AMD has published advisories with firmware fixes for host-level SEV-SNP issues.
Chip-level or physical attack Largely outside the chip makers' stated scope: Intel and AMD say physical attacks are out of scope. In October 2025, researchers showed with a memory-bus device costing under $1,000 that they could extract keys from Intel TDX and AMD SEV-SNP machines, in some cases including attestation keys, and AMD said it plans no mitigation. The attack needs physical access to the machine. Software side channels can often be patched by microcode updates, while physical bus attacks cannot, so data-centre physical security is the main defence.

Attestation shows what hardware and software started up. It does not show that answers are right. The researchers say extracted attestation keys can be used to fake a successful attestation. TEE.Fail needs physical access to a machine. Forging attestation is not only a physical-access problem: The Hacker News reported on 13 November, the day of this launch, that the Mior attack lets a malicious host change a VM's memory and forge signed SEV-SNP attestation reports, and that Skyfall lets one read VM data. AMD's advisory AMD-SB-3059 covers CVE-2026-0462, with SEV firmware dated 12 August 2026 and platform firmware targeted for December 2026. The advisory itself lists only the CVE; The Hacker News names it as the advisory for Mior, a finding from an ETH Zurich team. The same article reports that AMD published a separate advisory, AMD-SB-3061, for Skyfall (CVE-2026-40671), with platform firmware planned for November 2026. I could not confirm whether that firmware has shipped. These are attacks on the hardware class, not on Solana's code, but who runs the machine and which firmware it runs both matter.

Other limits to weigh

  • Beta status. It is unaudited, on devnet, and meant for development.
  • Hardware coverage. NVIDIA GPU attestation is not ready.
  • A public record. The onchain record shows the public signing key, hardware type and expiry date. Publishing it is the point, since it lets anyone check a signed answer. The side effect, which is my general observation and not a finding from the sources, is that outsiders can see which keys and hardware types are active.
  • Threat model. The product page is open about what stays visible and what you still trust: the user must trust the code the page serves, since encryption runs in it, and the model's enclave reads the prompt in order to run the model. The launch post is a short announcement and gives no formal threat model, and the product page links the Confidential Chat template, and the template's README is public on GitHub, but I could not find documentation or a public repository for the SDK or the onchain verifier program itself. Check what attestation guarantees against the project's documentation once it is published.
  • Trust in chip makers. TEE security rests on the hardware vendor's design and signing keys. Researchers have published attacks on TEEs before, so a TEE reduces trust in an operator but does not remove trust in the hardware. See the table above for what vendors and researchers have said.
  • Moving target. The product page now says plainly that the chat does not use the verifier yet. Wording and details changed within days of launch, so check the current pages before you build on any detail here. On 22 November the page still said mainnet follows the audit, with no date.

9. Questions to ask before relying on it

  1. Who runs the machines, and can I see the attestation for the exact ones serving my requests? The pages name Tinfoil's router for the chat's model and Nito for its own platform, but not who runs hardware for other developers. The template README says the host shown under each reply is not part of the proof.
  2. Who does the checking: my app, the browser, or the onchain record? The product page says the chat checks in the browser today, not onchain.
  3. Which software do I accept? The report identifies the software in the enclave, so decide which version you trust and who publishes it. The product page says each chat reply links the router's public build record and source code, which you can check. The template README says the browser verifies against a repository pinned in the page code.
  4. Which hardware and which expiry? The launch post says Intel TDX and AMD SEV-SNP, with NVIDIA GPU attestation in progress; the product page names AMD SEV-SNP on Google Cloud, AWS Nitro Enclaves and Google Confidential Space. Also ask which SEV-SNP firmware and attestation version the enclave reports, and whether it includes the fixes in AMD's published advisories, for example AMD-SB-3059, which AMD lists with platform firmware targeted for December 2026 on most EPYC lines.
  5. Is the visible metadata acceptable? IP addresses, account, model, timing and message size can be seen by intermediaries.
  6. What is the audit and mainnet plan? Until the audit is done and published, keep to testing.
  7. What happens when a key expires or a hardware flaw is disclosed? Ask how records are refreshed or revoked. I found nothing on this in the sources.
